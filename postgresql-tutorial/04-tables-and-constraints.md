# Chapter 4 — Tables and constraints

## What you'll learn

- How to design and create tables, and how to name things
- Identity columns, sequences, and why gaps in ids are normal
- Defaults, `NOT NULL`, `CHECK`, `UNIQUE`, primary keys and foreign keys, and what each one guarantees
- What happens to referencing rows when a referenced row is deleted (`ON DELETE`)
- Generated columns, virtual by default since PostgreSQL 18
- Domains: reusable types with built-in rules
- Changing tables with `ALTER TABLE`, and why DDL inside a transaction is a superpower
- The complete Inkwell schema, which the rest of the tutorial builds on

A table definition is a contract. Every rule you declare is checked on every insert and update, by every client,
forever. Rules you leave out end up being enforced (or not) by application code, which has bugs, gets bypassed by
scripts, and is rewritten every few years. The data outlives all of it. This chapter is about writing that contract.

## The Inkwell data model

Inkwell sells stationery online. Customers place orders; an order contains several products, each with a quantity and
the price paid; products belong to categories, which form a tree (Writing → Pens → Fountain pens); customers can review
products they bought.

```text
 customers 1───n orders 1───n order_items n───1 products n───1 categories ─┐
     │                                             │              ▲         │ parent_id
     └──────────────────1   n reviews n────────────┘              └─────────┘
```

`1───n` reads "one to many": one customer has many orders, each order belongs to one customer. The many-to-many
relationship between orders and products is represented by the `order_items` table in between. Chapter 14 discusses
modeling choices like these in depth; this chapter is about expressing them in SQL.

### Naming conventions

PostgreSQL doesn't care what you call things, but people do. This tutorial uses a widespread convention:

- Lower case with underscores (`order_items`), so names never need quoting.
- Plural table names (`customers`), singular column names (`email`).
- A surrogate primary key called `id`; a foreign key called `<singular table>_id` (`customer_id`).
- Timestamps end in `_at` (`created_at`, `shipped_at`), dates in `_on` or `_date`, booleans read as a statement
  (`active`, `is_gift`).
- Constraint and index names `<table>_<column>_<kind>`, which is also what PostgreSQL generates when you don't name
  them (`customers_email_key`, `orders_customer_id_fkey`).

## Creating a table

```sql
CREATE TABLE customers (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL UNIQUE
                CONSTRAINT customers_email_lowercase CHECK (email = lower(email)),
    full_name   text NOT NULL CHECK (full_name <> ''),
    country     text NOT NULL CHECK (country ~ '^[A-Z]{2}$'),
    created_at  timestamptz NOT NULL DEFAULT now()
);
```

```text
CREATE TABLE
```

Each column has a name, a type, and optionally a default and constraints. Let's go through the parts.

### Identity columns

`id bigint GENERATED ALWAYS AS IDENTITY` makes PostgreSQL number new rows automatically: 1, 2, 3, … Behind the scenes
it creates a **sequence**, a special counter object, and takes the next value from it for every insert.

- `GENERATED ALWAYS` means the database always picks the value; an `INSERT` that supplies one is an error (unless it
  says `OVERRIDING SYSTEM VALUE`, which is for data migrations).
- `GENERATED BY DEFAULT` lets an `INSERT` supply its own value and generates one only when it doesn't. That is
  convenient but invites collisions: insert id 5 by hand, and the sequence will later hand out 5 again.

You'll often see the older `serial` and `bigserial` pseudo-types in existing schemas (`id serial PRIMARY KEY`). They
create a sequence and a `DEFAULT nextval(...)`, which behaves like `BY DEFAULT`. Identity columns are the SQL-standard
replacement and have cleaner permissions and copying behaviour; use them in new tables.

**Ids have gaps, and that's fine.** A sequence never goes backwards: a value handed out to an insert that then fails
or is rolled back is gone. Sequences are deliberately not transactional, so that concurrent inserts never wait for each
other. Never rely on ids being consecutive, and never show them to users as "order number 1, 2, 3" if gaps would
confuse anyone. (If you need gap-free numbering, such as invoice numbers in some jurisdictions, that needs a separate,
locked counter; chapter 17 shows how.)

### Defaults

`created_at timestamptz NOT NULL DEFAULT now()` gives the column a value when an `INSERT` doesn't mention it. A default
can be any expression without subqueries: a constant (`DEFAULT 0`, `DEFAULT '{}'`), or a function call
(`DEFAULT now()`, `DEFAULT gen_random_uuid()`). It is evaluated per row at insert time.

A default is only a suggestion: an `INSERT` can still store any other valid value, including `NULL` unless the column
is `NOT NULL`. A default is not a constraint.

### NOT NULL

`NOT NULL` forbids missing values. Make it your default for every column, and leave it off only when "unknown" or "not
applicable" is a real state. Nullable columns spread complexity everywhere: every query, report and application line
that reads them has to handle the `NULL` case (chapter 6 shows how easy that is to get wrong).

Since PostgreSQL 18, `NOT NULL` constraints are stored with names like every other constraint (here
`customers_email_not_null`), which `\d+` lists and `ALTER TABLE` can refer to.

### CHECK constraints

A `CHECK` constraint is a boolean expression that every row must satisfy:

- `CHECK (full_name <> '')` forbids empty names (`NOT NULL` alone allows `''`).
- `CHECK (country ~ '^[A-Z]{2}$')` requires two upper-case letters, using a regular expression match (`~`, chapter 11).
- `CHECK (email = lower(email))` requires emails to be stored in lower case, so that `Ana@Example.com` and
  `ana@example.com` can't both be registered. The application must lower-case emails before storing them; the
  constraint makes sure it never forgets.

Give constraints names when the generated name wouldn't be clear: `CONSTRAINT customers_email_lowercase CHECK (...)`.
The name appears in error messages, and applications can map it to a friendly message ("emails must be lower case").

A subtle but important rule: **a `CHECK` passes when the expression is `NULL`**, not only when it is true. Only `false`
is a violation. So `CHECK (price >= 0)` on a nullable `price` column allows `NULL`. Combine `CHECK` with `NOT NULL`
when the value is required.

A `CHECK` constraint can only look at the row being written. It can't query other rows or other tables (that is what
`UNIQUE`, foreign keys, exclusion constraints and triggers are for), and it should be **immutable**: an expression like
`CHECK (created_at <= now())` seems to work but isn't re-checked as time passes, and breaks restoring a dump.

### UNIQUE

`email text NOT NULL UNIQUE` guarantees that no two rows have the same email. PostgreSQL enforces it with a unique
index (here called `customers_email_key`), which also makes lookups by email fast.

A unique constraint can span several columns, `UNIQUE (product_id, customer_id)`, meaning the *combination* must be
unique. And by default `NULL`s are not considered equal to each other, so a unique column can contain any number of
`NULL`s. PostgreSQL 15 added `UNIQUE NULLS NOT DISTINCT` for the cases where at most one `NULL` should be allowed.

### Primary keys

`PRIMARY KEY` is `UNIQUE` plus `NOT NULL`, and declares the column (or columns) as *the* way to identify a row. A table
can have only one. Every table should have one: replication, many tools and ORMs, and your own sanity depend on it.

Here the key is a **surrogate key**, a meaningless generated number. The alternative is a **natural key** made of real
data, like the email or a product's SKU. Natural keys change (people change emails), so most tables use a surrogate
primary key and add `UNIQUE` constraints on the natural keys. Chapter 14 goes into the trade-offs.

## Foreign keys and the category tree

Categories form a tree: each category has an optional parent.

```sql
CREATE TABLE categories (
    id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    parent_id  integer REFERENCES categories (id),
    name       text NOT NULL,
    slug       text NOT NULL UNIQUE CHECK (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$')
);
```

```text
CREATE TABLE
```

`parent_id integer REFERENCES categories (id)` is a **foreign key**: every non-null `parent_id` must be the `id` of an
existing category. A table can reference itself, as here. `parent_id` is nullable because top-level categories have no
parent. The `slug` is the URL-friendly name (`fountain-pens`), restricted to lower-case words joined by hyphens.

A `categories` table uses an `integer` key: a shop will never have two billion categories.

### Products

```sql
CREATE TABLE products (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku          text NOT NULL UNIQUE,
    name         text NOT NULL,
    description  text NOT NULL DEFAULT '',
    category_id  integer NOT NULL REFERENCES categories (id),
    price        numeric(10, 2) NOT NULL CHECK (price >= 0),
    stock        integer NOT NULL DEFAULT 0 CHECK (stock >= 0),
    attributes   jsonb NOT NULL DEFAULT '{}',
    tags         text[] NOT NULL DEFAULT '{}',
    active       boolean NOT NULL DEFAULT true,
    created_at   timestamptz NOT NULL DEFAULT now()
);
```

```text
CREATE TABLE
```

- `sku` (stock-keeping unit) is the shop's own product code: a natural key, so it is `UNIQUE`.
- `description` defaults to an empty string rather than allowing `NULL`: "no description" is just empty text.
- `CHECK (stock >= 0)` makes overselling impossible at the database level. When two customers buy the last fountain
  pen at the same moment, one of the two updates will fail this check rather than leave the stock at −1. Chapter 17
  builds on that.
- `attributes jsonb` holds product-specific details such as nib size or paper weight, which differ by product type.
  Chapter 12 covers JSON; for now it defaults to an empty JSON object.
- `tags text[]` is an array of free-form labels such as `gift` or `bestseller`.
- `active` lets the shop hide discontinued products without deleting them, because old orders still reference them.

### Orders

```sql
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'delivered', 'cancelled');

CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  bigint NOT NULL REFERENCES customers (id),
    status       order_status NOT NULL DEFAULT 'pending',
    created_at   timestamptz NOT NULL DEFAULT now(),
    shipped_at   timestamptz,
    CONSTRAINT orders_shipped_after_created
        CHECK (shipped_at >= created_at),
    CONSTRAINT orders_shipped_at_matches_status
        CHECK ((status IN ('shipped', 'delivered')) = (shipped_at IS NOT NULL))
);
```

```text
CREATE TYPE
CREATE TABLE
```

The two constraints at the end are **table constraints**: written after the columns because they involve more than one
column (a column constraint can only mention its own column, though PostgreSQL is lenient about this for `CHECK`).

- `orders_shipped_after_created`: an order can't ship before it was placed. When `shipped_at` is `NULL`, the
  expression is `NULL`, and the check passes, which is exactly right for unshipped orders.
- `orders_shipped_at_matches_status`: a boolean compared with a boolean. Shipped and delivered orders must have a
  `shipped_at`; all others must not. Rules like this keep two columns from contradicting each other, a common source
  of bugs where one part of the application updates `status` and forgets `shipped_at`.

### Order items: composite keys and ON DELETE

```sql
CREATE TABLE order_items (
    order_id    bigint NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    product_id  bigint NOT NULL REFERENCES products (id),
    quantity    integer NOT NULL CHECK (quantity > 0),
    unit_price  numeric(10, 2) NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)
);
```

```text
CREATE TABLE
```

- The primary key is **composite**: an order contains each product at most once (with a quantity), so the pair
  `(order_id, product_id)` identifies a line. No separate `id` is needed.
- `unit_price` is a copy of the product's price **at the time of the order**. Prices change; what a customer paid
  must not. Copying it is not redundancy, it is history.
- `ON DELETE CASCADE` on `order_id`: deleting an order deletes its lines too. They have no meaning without it.
- `product_id` has no `ON DELETE` clause, so it gets the default, `NO ACTION`: deleting a product that appears in any
  order is refused. That protects order history; you deactivate products instead.

The options for `ON DELETE` (and `ON UPDATE`, for changes to the referenced key):

| Action | When the referenced row is deleted |
|---|---|
| `NO ACTION` (default) | error if referencing rows exist (checked at the end of the statement) |
| `RESTRICT` | error if referencing rows exist (checked immediately; rarely different in practice) |
| `CASCADE` | delete the referencing rows too |
| `SET NULL` | set the foreign key column(s) to `NULL` |
| `SET DEFAULT` | set the foreign key column(s) to their default |

Use `CASCADE` for rows that are *part of* the parent (order lines, an order's notes) and the default for references to
independent things (a product, a customer). Cascading deletes across independent entities are how one careless
`DELETE` wipes out years of data.

A customer can review each product once, and a review may have no text (`body` is nullable: a star rating alone is a

### Index your foreign keys

PostgreSQL automatically creates an index for every primary key and unique constraint, but **not** for the
referencing side of a foreign key. Without one, two common operations get slow on big tables: joining from the parent
to its children (`orders` of a customer), and deleting or updating a parent row, because PostgreSQL must check every
child table for references, which without an index is a full scan of each.

Create an index on every foreign key column that isn't already the first column of another index:

```sql
CREATE INDEX categories_parent_id_idx ON categories (parent_id);
CREATE INDEX products_category_id_idx ON products (category_id);
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
CREATE INDEX order_items_product_id_idx ON order_items (product_id);
CREATE INDEX reviews_customer_id_idx ON reviews (customer_id);
```

```text

CREATE INDEX
```

## Generated columns

A **generated column** is computed from other columns of the same row. PostgreSQL 18 supports two kinds:

- **Virtual** (the default since 18): computed when the row is read, taking no storage.
- **Stored**: computed when the row is written and stored like a normal column. It can be indexed. Before 18, this was
  the only kind, and the `STORED` keyword was required.

Try both on a scratch table:

```sql
CREATE TABLE gen_demo (
    quantity    integer NOT NULL,
    unit_price  numeric(10, 2) NOT NULL,
    line_total  numeric GENERATED ALWAYS AS (quantity * unit_price),
    with_vat    numeric GENERATED ALWAYS AS (round(quantity * unit_price * 1.2, 2)) STORED
);

INSERT INTO gen_demo (quantity, unit_price) VALUES (3, 14.00);
SELECT * FROM gen_demo;
```

```text
(1 row)
```

The expression may only use columns of the same row and immutable functions. Generated columns are good for derived
values you query or filter on often, such as a normalized search key or a full-text search document (chapter 13 uses a
stored one). Virtual columns can't be indexed in PostgreSQL 18; use `STORED` when you need an index.

## Domains

A **domain** is a data type with constraints attached, defined once and used in many tables:

```sql
CREATE DOMAIN money_amount AS numeric(10, 2) CHECK (VALUE >= 0);
SELECT (-1)::money_amount;
```

```text
CREATE DOMAIN
ERROR:  value for domain money_amount violates check constraint "money_amount_check"
```

`VALUE` stands for the value being checked. Domains are a neat way to express "an email address" or "a positive
amount" consistently across a schema. The downsides: changing a domain's constraint later affects every column using
it at once, and error messages name the domain rather than the table. Inkwell keeps its checks on the columns, so drop
this one:

```sql
DROP DOMAIN money_amount;
```

```text
DROP DOMAIN
```

## Changing tables: ALTER TABLE

Schemas evolve. `ALTER TABLE` adds, changes and removes columns and constraints:

```sql
ALTER TABLE customers ADD COLUMN phone text;
ALTER TABLE customers ADD CONSTRAINT customers_phone_format CHECK (phone ~ '^\+[0-9]{7,15}$');
ALTER TABLE customers RENAME COLUMN phone TO phone_number;
ALTER TABLE customers DROP COLUMN phone_number;
```

```text
ALTER TABLE
ALTER TABLE
ALTER TABLE
ALTER TABLE
```

Dropping the column also dropped the constraint on it. Other common forms:

| Statement | Purpose |
|---|---|
| `ALTER TABLE t ALTER COLUMN c SET DEFAULT expr` / `DROP DEFAULT` | change the default |
| `ALTER TABLE t ALTER COLUMN c SET NOT NULL` / `DROP NOT NULL` | add or remove `NOT NULL` |
| `ALTER TABLE t ALTER COLUMN c TYPE newtype [USING expr]` | change the type, converting existing values |
| `ALTER TABLE t DROP CONSTRAINT name` | remove a constraint |
| `ALTER TABLE t RENAME TO new_name` | rename the table |

On a table with data in it, adding a constraint checks every existing row, and some changes rewrite the whole table.
Both hold a lock that blocks other sessions for the duration. On a big, busy production table that matters a lot:

- `ADD COLUMN` with no default or a constant default is instant. (A volatile default like `clock_timestamp()` forces a
  rewrite.)
- `ALTER COLUMN ... TYPE` usually rewrites the table and all its indexes. Changing `integer` to `bigint` on a table
  with a billion rows can take hours, which is why chapter 3 said to choose `bigint` up front.
- `ADD CONSTRAINT ... CHECK` or `FOREIGN KEY` can be split in two: add it with `NOT VALID` (instant; enforced for new
  rows only) and later run `ALTER TABLE ... VALIDATE CONSTRAINT name`, which checks old rows without blocking writes.
  PostgreSQL 18 extends `NOT VALID` to `NOT NULL` constraints.

Chapter 17 covers the locking side of schema changes in detail.

### NOT ENFORCED constraints (PostgreSQL 18+)

> **Just a taste — you don't need to learn or fully understand this now.** PostgreSQL 18 can record a `CHECK` or
> foreign key constraint without enforcing it, mostly for documenting rules that are enforced elsewhere (for example,
> in a data warehouse loaded from a trusted source).

```sql
ALTER TABLE orders ADD CONSTRAINT orders_id_positive CHECK (id > 0) NOT ENFORCED;
ALTER TABLE orders DROP CONSTRAINT orders_id_positive;
```

## Transactional DDL

In PostgreSQL, schema changes are transactional, like data changes. You can try a change and take it back:

```sql
BEGIN;
DROP TABLE reviews;
\dt reviews
ROLLBACK;
\dt reviews
```

```text
BEGIN
DROP TABLE
Did not find any tables named "reviews".
ROLLBACK
           List of tables
 Schema |  Name   | Type  |  Owner
--------+---------+-------+----------
 public | reviews | table | postgres
(1 row)
```

Inside the transaction the table is gone; after `ROLLBACK` it is back, with its data. That makes migrations safe: run
the whole migration in one transaction, and if any step fails, nothing has changed. Many databases can't do this; in
PostgreSQL only a few statements (such as `CREATE DATABASE`, `CREATE INDEX CONCURRENTLY` and `VACUUM`) can't run inside
a transaction block.

## Dropping things

`DROP TABLE` removes a table and its data. It refuses if other objects depend on it:

```sql
DROP TABLE customers;
```

```text
ERROR:  cannot drop table customers because other objects depend on it
DETAIL:  constraint orders_customer_id_fkey on table orders depends on table customers
constraint reviews_customer_id_fkey on table reviews depends on table customers
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

`DROP TABLE customers CASCADE` would drop the foreign key constraints on `orders` and `reviews` (not those tables
themselves). `CASCADE` on a `DROP` is a sharp tool: read what it will remove, which the error message above conveniently
lists, before using it.

## Temporary and unlogged tables

Two variations on `CREATE TABLE` are worth knowing:

- `CREATE TEMPORARY TABLE` (or `TEMP`) creates a table visible only to your session, dropped automatically when you
  disconnect. Useful for intermediate results in scripts and reports.
- `CREATE UNLOGGED TABLE` skips the write-ahead log, making writes much faster, at a price: the table is emptied after
  a crash and is not replicated to standby servers. Only for data you can rebuild, such as a cache or a staging area
  for imports.

```text
 public | orders      | table | postgres
 public | products    | table | postgres
 public | reviews     | table | postgres
(6 rows)
```

## Key takeaways

- Declare every rule you can in the schema: types, `NOT NULL`, `CHECK`, `UNIQUE`, primary and foreign keys. They hold
  no matter which program or person writes the data.
- Use `bigint GENERATED ALWAYS AS IDENTITY` for surrogate keys. Sequences leave gaps; never depend on consecutive ids.
- `CHECK` passes on `NULL`. Combine it with `NOT NULL` when a value is required. Checks see only the current row.
- `UNIQUE` and `PRIMARY KEY` create indexes; foreign keys don't. Index foreign key columns yourself.
- Choose `ON DELETE CASCADE` for rows that are part of their parent, and the default (`NO ACTION`) for references to
  independent entities.
- Copy values that are history (the price paid) instead of referencing values that change.
- Generated columns are virtual by default in PostgreSQL 18; use `STORED` when you need to index them.
- DDL is transactional: wrap schema changes in a transaction. On large tables, know which `ALTER TABLE` forms rewrite
  the table or take long locks, and use `NOT VALID` + `VALIDATE` for new constraints.

## Exercises

1. **Read the constraints.** Without running anything, decide which of these inserts succeed. Then run them to check.
   (Assume customer 1 exists and the `categories` table is empty.)

   ```sql
   INSERT INTO categories (name, slug) VALUES ('Writing', 'writing');
   INSERT INTO categories (name, slug) VALUES ('Fountain Pens', 'Fountain-Pens');
   INSERT INTO categories (name, slug, parent_id) VALUES ('Pens', 'pens', 999);
   INSERT INTO reviews (product_id, customer_id, rating) VALUES (1, 1, 6);
   ```

<details>
<summary>Solution</summary>

Only the first succeeds.

- The second violates `categories_slug_check`: the slug must be lower case.
- The third violates `categories_parent_id_fkey`: there is no category 999.
- The fourth fails twice over (rating 6 is out of range, and product 1 doesn't exist). PostgreSQL reports the first
  violation it finds: here the `CHECK` constraint `reviews_rating_check`, because checks are evaluated before foreign
  keys.

Remove the test category afterwards: `DELETE FROM categories;`. (Chapter 5 starts from empty tables anyway.)

</details>

2. **Discounts.** Inkwell wants to store discount codes: a unique code (upper-case letters and digits, 4–12
   characters), a percentage between 1 and 90, an optional expiry moment, and a usage limit that, if present, must be
   positive. Write the `CREATE TABLE discount_codes` statement, then test it with one valid and two invalid inserts.

<details>
<summary>Solution</summary>

```sql
CREATE TABLE discount_codes (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code         text NOT NULL UNIQUE CHECK (code ~ '^[A-Z0-9]{4,12}$'),
    percent_off  integer NOT NULL CHECK (percent_off BETWEEN 1 AND 90),
    expires_at   timestamptz,
    usage_limit  integer CHECK (usage_limit > 0),
    created_at   timestamptz NOT NULL DEFAULT now()
);

INSERT INTO discount_codes (code, percent_off) VALUES ('WELCOME10', 10);       -- ok
INSERT INTO discount_codes (code, percent_off) VALUES ('welcome', 10);         -- fails: lower case
INSERT INTO discount_codes (code, percent_off, usage_limit) VALUES ('X99Y', 20, 0);  -- fails: usage_limit
```

`expires_at` and `usage_limit` are nullable because "no expiry" and "unlimited" are real states, and `NULL` expresses
"no limit" well here. `CHECK (usage_limit > 0)` still allows `NULL`, which is what we want. Drop the table when you
are done: `DROP TABLE discount_codes;`.

</details>

3. **Cascade or not?** For each relationship, choose an `ON DELETE` action and justify it: (a) a product's photos
   (`product_photos.product_id`), (b) an order's assigned courier (`orders.courier_id`, where couriers can be removed
   from the system but the order history must stay), (c) a review's customer (`reviews.customer_id`) when a customer
   deletes their account under a privacy law.

<details>
<summary>Solution</summary>

- (a) `ON DELETE CASCADE`: photos are part of the product and meaningless without it.
- (b) `ON DELETE SET NULL` on a nullable `courier_id`: the order stays, it just no longer points to a courier.
  (Alternatively keep couriers forever and mark them inactive, like products, if you need to know who delivered.)
- (c) It depends on the policy, which is the point: `CASCADE` deletes the reviews with the account; `SET NULL` (with a
  nullable `customer_id`) keeps the reviews anonymously. Many shops prefer not to hard-delete at all, and instead
  anonymize the customer row (replace the name and email) so that orders and reviews keep valid references. The
  database can enforce whichever rule you choose, but it can't choose for you.

</details>

4. **Evolve the schema safely.** Add a `phone` column to `customers` that must, when present, start with `+` followed by
   7 to 15 digits. Do it in a transaction, using `NOT VALID` and `VALIDATE` for the constraint, and check the result with
   `\d customers`. Then roll the whole thing back, since Inkwell doesn't need phone numbers yet.

<details>
<summary>Solution</summary>

```sql
BEGIN;
ALTER TABLE customers ADD COLUMN phone text;
ALTER TABLE customers
    ADD CONSTRAINT customers_phone_format CHECK (phone ~ '^\+[0-9]{7,15}$') NOT VALID;
ALTER TABLE customers VALIDATE CONSTRAINT customers_phone_format;
\d customers
ROLLBACK;
```

Inside the transaction `\d customers` shows the new column and the constraint. On an empty or small table `NOT VALID`
makes no difference, but on a large production table, adding the constraint with `NOT VALID` is instant, and
`VALIDATE` scans the existing rows with a weaker lock that doesn't block inserts and updates. (In a real migration
you'd run the two steps in separate transactions so the weaker lock actually helps.) After `ROLLBACK`, the table is
unchanged.

</details>

5. **Gap-free invoice numbers.** Explain why an identity column is a bad fit for legally required gap-free invoice
   numbers, and sketch a table design that could provide them. (You'll implement it properly in chapter 17.)

<details>
<summary>Solution</summary>

Identity values come from a sequence, which is non-transactional: a value used by an insert that fails or rolls back
is never reused, so gaps appear. That is deliberate, because it lets concurrent transactions get ids without waiting
for each other.

A gap-free design uses an ordinary counter row that is updated inside the same transaction as the invoice insert:

```sql
CREATE TABLE invoice_counters (
    year         integer PRIMARY KEY,
    last_number  integer NOT NULL
);
-- In the transaction that creates an invoice:
-- UPDATE invoice_counters SET last_number = last_number + 1 WHERE year = 2026 RETURNING last_number;
-- INSERT INTO invoices (year, number, ...) VALUES (2026, <that number>, ...);
```

If the transaction rolls back, the counter update rolls back with it, so no number is lost. The price is that
concurrent invoice creation is serialized on that one counter row: each transaction waits until the previous one
commits. That is fine for invoices, and a reason not to use this design for anything high-volume.

</details>
